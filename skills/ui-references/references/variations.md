# Compare directions when the choice matters

Adapted from Mobbin's MIT-licensed explore workflow. See [upstream notices](../UPSTREAM.md).

Use this only when the user asks for alternatives or the reference research exposes materially different solutions. A clear polish request can proceed directly.

1. Choose one decision to compare: density, hierarchy, navigation or control arrangement. Keep the job, content, platform, kit and baseline the same.
2. Build two or three distinct directions from their own inspected examples. Do not create filler variants. Label directions backed by only one product as examples, not corroborated precedent.
3. Keep the variants isolated from the production implementation. Use an available writable design tool or a temporary code mockup with the existing kit; neither a canvas subscription nor image generation is required.
4. Capture every variant at the same viewport and state beside the actual baseline. Name exactly what differs and show which references demonstrate it. A static mockup cannot establish functioning interaction.
5. Recommend the direction that best serves the job and constraints. Apply an already authorized direction; ask only if the remaining choice materially changes product behaviour or the requested design scope.

Do not require parallel agents or multiple providers. Do not average incompatible directions. The eventual implementation still goes through the full capture, interaction and design-kit checks.
